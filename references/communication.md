# 清楚表达、案例与图表

## 让人直接理解

先回答问题，再解释理由。一个段落讲清一个主要判断；沿事情如何发生、为什么如此、怎样改变展开。默认给足用户所需的实质内容，不以精简为由省去关键论证、取舍、条款或失败边界；也不把重复分析搬到正文充当深度。

完整性以[完整答案与成果](complete-answer.md)为准：所有已开展的实质分析及其论证默认进入正文，不得仅因次要或不改变主结论而删除。不设置默认字数上限；复杂问题需要上万字就充分展开，超过单次消息容量时连续交付并保留完整文件。先说结论是阅读顺序，不是省略后文的理由。

用具体主体、动作和结果解释抽象概念。例如，讨论“有效反馈”时，先说投诉有没有进入决定、谁能修改决定、修改有没有真正发生。需要专有名词时，在首次出现处用一句话解释它增加了什么区别。删除术语后，读者仍应理解结论的依据和方案的作用。

不按内部阶段编号写文章，不给用户堆叠G/C/HV/SJ等标签，不把“复杂”“多维”“系统性”作为机制说明的替代。对受影响者的经验认真说明，不暗示只有懂术语的人才有资格参与判断。

## 真实案例怎样支持判断

涉及经验机制、组织制度、历史变化或方案效果时，主动寻找与关键判断可比较的真实案例。优先一手资料、原始研究、官方记录和可追溯当事材料；区分原始来源与转述。核对关键事实并给可访问出处，说明时间、背景及与当前问题的相同和不同处。

案例应承担明确作用：支持某个机制、显示某种成本、提供可行做法，或反驳过强主张。一个著名案例不证明普遍规律，案例中同时出现的现象不自动构成因果，别的制度可行不保证这里可复制。不要只在结尾附上一段故事装饰结论。

只有相关可靠案例才能进入支持链。缺少可核案例时说明缺口并完成仍有依据的判断，不编造细节、不把案例当每个算术或定义题的门槛。用户限定材料时尊重范围；虚构情景、教学例和结构类比清楚标明，不能伪装成真实案例。

## 主动选择有用的图表

图表能减少阅读负担时主动制作，不要求用户额外提出：

| 信息形态 | 合适形式 | 关键要求 |
| --- | --- | --- |
| 作用通道、因果链、反馈回路 | 简洁关系图或因果图 | 区分有材料支持的边、推测边和拟议干预；相关不画成已证因果 |
| 多个方案、成本与收益、保留与修改 | 比较表 | 同一比较口径，写出最终取舍；不以整齐表格掩盖未知 |
| 办事、申诉、裁决与救济 | 流程图 | 谁负责、何时分支、哪里能纠错，图与条款一致 |
| 时间、资源容量、工作安排 | 时间线或排程表 | 标单位、期限和容量，不能只画各自可行而整体超载的任务 |
| 数量与趋势 | 数据图 | 使用真实或明确标注的示例数据，轴、单位和来源齐全 |
| 多条件变化或方案探索 | 宿主支持时采用交互图或独立HTML | 保留静态说明和可读结论；不存在交互能力时用简单图表完成 |

使用当前宿主实际支持的形式。可渲染的Mermaid适合简洁关系与流程；需要更直观的交互且有可用工具时使用相应能力。避免为了图表引入大型依赖、部署或无关设计工作；不要让技能依赖某一特定插件。

图前说明要看什么，图后解释它如何支持判断。图中用普通词，关系不宜过密；大图按问题拆开。输出带一段文字解释，确保看不到颜色或图像时仍能理解。图只是表达证据与方案的方式，不能替代论证或制造精确感。

## 决策成果的阅读顺序

结论与首选 → 关键事实与真实案例 → 决定性关系和必要图表 → 其他方案为何落选 → 具体方案/条文/计划 → 代价、实施条件和改判条件。

这是可调整的阅读顺序，不是每题固定的七段模板。小问题直接回答；大问题让读者先看到方向，再按需要深入。引用靠近所支持的内容，资料与工作记录另存，正文不塞入迭代解说和运行日志。
