# 组织与工作：职责和共享资源安排

配套[可查询数据](../../assets/domains/organization-work.json)包含9项记录与一段有来源的领域说明；调用方法见[领域包入口](README.md)。以下教学例不作为数据包的现实实例。

## 适用任务

用于采用 Scrum Guide 2020 语义的团队：解释谁承担哪类职责，核对某项工作是否达到明示完成条件，并检查多项任务能否共享设备、环境或人员时段。若团队只是借用了“Product Owner”“Sprint”等名称，先以实际制度材料定其义项，不把 Scrum 定义强加给它。

本包不判定劳动法责任、采购权、预算权或发布许可。那些资格需要适用规则和具体授权材料；专业角色名称不能代证。排程也不代表成员同意加班或具备工作资格。

## 来源与已核范围

| 来源 | 版本、实际正文位置 | 可支持的范围 |
|---|---|---|
| [O1：Ken Schwaber、Jeff Sutherland，Scrum Guide](https://scrumguides.org/scrum-guide.html) | November 2020；Scrum Team、Developers、Product Owner、Scrum Master、Increment、Definition of Done；正文查阅 2026-11-17 | 该框架的职责及完成语义。不能证明现实团队实际依此运转 |
| [O2：Google OR-Tools，The Job Shop Problem](https://developers.google.com/optimization/scheduling/job_shop) | 在线官方指南，页面未给出本包可锁定的固定发布版本；已读问题定义、示例、变量与约束、目标；正文查阅 2026-11-17 | 有前后次序、同资源互斥且任务不可中断的排程模型。不是所有人员工作的通用假设 |

O1 中，Product Owner 承担产品价值及 Product Backlog 管理职责；部分工作可委派，相关 accountability 不因此自动转移。Developers 制订 Sprint 计划并遵守 Definition of Done；Scrum Master 负责建立 Scrum 并支持团队有效性。Increment 必须可用并符合 Definition of Done。以上只说明框架用法。[O1](https://scrumguides.org/scrum-guide.html)

O2 将任务开始时间联合求解，同时保留前置次序、机器互斥和连续加工约束；它以总完工跨度为目标。本包只借用相应约束表达，不默认这个目标适合用户。[O2](https://developers.google.com/optimization/scheduling/job_shop)

## 名词、动作和角色关系

以下是任务取证接口。来源词义见上文；表中的证据要求及输出限制是工作设计。

| 任务说法 | 需要分开的动作或关系 | 具体实例所需材料 | 不可自动推出 |
|---|---|---|---|
| “负责人” | 排序需求、安排工作、执行、验收、批准发布 | 岗位／项目规则及本次委派、接受、实际执行记录 | 一人拥有所有动作权限；职称等于法律责任 |
| “已委派” | 请求他人执行；对方接受；职责是否按适用规则转移 | 委派对象、内容、时间和有效规则 | 发出消息就完成交接 |
| “Done” | 达到采用版本的质量条件；实际发布；用户使用结果 | 条目、Definition of Done 版本、核验结果、发布记录 | 三个终点同时成立 |
| “资源可用” | 日历空闲、技能匹配、访问资格、实际可以连续占用 | 容量日历、技能／资格依据、必要连续时段 | 总工时足够即每项任务可安排 |
| “收到反馈” | 收到、理解、作出处理、处理落实 | 消息、处理理由、决定版本、后续状态 | 必须改变原决定；已经产生后果 |
| “接班完成” | 交出材料、接任者能操作、权限生效、待命关系终止 | 接收核验、操作演练、权限状态、剩余安排 | 原执行者仍无限待命才算负责 |

不得把 Product Owner 译为所有场景中的“最终审批人”，也不得把 Scrum Master 直接译为行政主管。实际角色实例化需有本地材料；没有材料可先解释框架角色，实例身份保持未知。

## 字段、单位、分母与时间

以下字段按任务选用，不是 O1 或 O2 规定的通用表单：

| 字段 | 用法与口径 |
|---|---|
| `task_id`、`endpoint`、`done_definition_version` | 同一工作标识与本次终点；“代码已提交”和“服务已发布”分别记录 |
| `actor_id`、`role_basis`、`allowed_action` | 角色依据与具体动作资格；人能做、制度允许做和实际已做分列 |
| `duration`、`duration_unit`、`splittable` | 工时或日历时长须明确；未知时长不填零；不可拆分需连续时间 |
| `resource_id`、`capacity_calendar`、`required_capacity` | 同一环境或同一人不能因在两张表出现就重复计算容量 |
| `predecessors`、`earliest_start`、`deadline` | 顺序、时区、工作日历、硬期限或可协商期限分别声明 |
| `arrangement_owner`、`execution_owner`、`on_call_window` | 安排、执行与待命可由不同人承担；没有实际安排时保持待核 |
| `received_at`、`decided_at`、`effective_at` | 收到、决定和实际生效不可用同一个时间代替 |
| `completion_numerator`、`completion_denominator` | 若报完成率，固定同批任务、纳入／移除规则、截止及完成口径；取消任务另列，不能静默缩小分母 |

## 专业方法与处理步骤

先用采用版本及本地职责文件解释词义，再查实际承接。对共享资源问题建立前后依赖和时段约束；只在任务确实不可拆分时采用 O2 的连续加工假设。若人的工作包含切换、休息、并行监控或资格限制，在任务模型中另列，不能把人直接当机器。

返回可行排程时附开始／结束和资源分配见证；证明不可行须针对明确模型；预算内未找到解不等于不可行。需要改变期限、降低范围或增加容量时，形成新方案并保留原承诺结果。角色解释足够解决的问题不必运行排程模型。

反馈核对以任务终点为限：收到反馈已经是一个事实；是否改变后续须另查。维持有依据的原决定可以是合理处理，不能拿改判率替代处理质量。

## 与理论的有限对应

| 对应身份 | 可借用的区别 | 对应边界 |
|---|---|---|
| 部分对应，待检验 | §7.3.5 行动承接层：框架问责、实际执行与维护的岗位或个人、决定与授权、停止权和受益分开；委派的提出、接收、执行与问责是否转移分别记录 | 不把所有框架 accountability 合并成一种责任，更不由记录直接定责；承接能力不产生无限承接义务 |
| 部分对应，待检验 | §7.3.7 反馈写回：提交与受理凭证、字段前后版本、实际执行、生效与持续分别观察 | 只到达、只受理或只表态不是有效写回；有理由维持原决定也可以完成程序责任 |
| 观察接口，待检验 | §7.3.9 结构负荷：同一窗口内的余量、积压与恢复，以及可用整段的长度与可预期性 | 总时数相同可以对应很不同的连续时段，不把零散空闲相加成同一容量 |
| 观察接口，待检验 | §7.6 的实践问题连接分配与实践机会记录 | 任务反复交给熟手，只是线索；不能直接证明分配造成能力差异 |
| 工作方法连接 | §12.10.2 与附录 C.12：共享容量、人员和停止通道的联合可行性 | 模型可行不证明实际资格、同意或执行成立；下期增容补不回本期已错过的期限 |
| 部分对应，待检验 | §13.11.2 任务终点：Definition of Done 只界定 Increment 的完成 | 发布、外部状态变化与用户后果各有终点和证据，不能由前一环节的成功回执代替 |
| 领域定位 | 附录 D.16；正式表述转义按 §3.4.1 另核 | 不因词义对齐宣布形成了正式经验实例 |

## 输出例与容易混淆的反例

**教学设定，非真实团队记录。** A、B 两项验证均需独占测试环境两小时，都只能在09:00后开始，均要求12:00前完成。环境只有一套，任务不可拆分，且无其他可用环境。记录另写“开发已完成”，但未给发布授权。

可输出：“两项验证分别可以在三小时窗口内完成，但共同需要四小时独占时间，当前模型下不能同时按期完成。可比较增加环境或改变其中一项期限；后一方案不使原期限自动达成。‘开发已完成’目前只支持该记录的完成口径，是否满足采用的 Definition of Done 及发布许可仍需对应材料。”

反例：同样四小时工作若可真正并行、另有资源或期限不同，上述不可行结论不再适用。另一个反例是意见已被审阅且原决定仍正确；没有改动不能单独证明反馈无效。职责名称相同、授权规则不同的两个机构，也不能复用同一审批链。

## 变更复核与退出

Scrum 采用版本、Definition of Done、本地职责和委派、资源容量、工作资格、截止或统计分母变化时，只复核相关判断。若本地不用 Scrum，则保留排程方法，撤回不适用的角色定义；不以“偏离框架”替代对当地事实的描述。真实组织证据不足时可交付词义解释、可行性条件或资料清单，不补造具体执行情况。
