# 技术系统与维护：HTTP服务的观测与恢复

配套[可查询数据](../../assets/domains/technical-maintenance.json)包含10项记录与一段有来源的领域说明；调用方法见[领域包入口](README.md)。以下教学例不作为数据包的现实实例。

## 适用任务

用于核对一个有明确端点和用户任务的 HTTP 服务：请求是否被接受、操作是否完成、所测服务是否达到声明目标、故障后恢复到何种范围，以及执行维护动作需要什么实际权限。系统版本、路由、调用方身份和时间范围都应明确。

本包不覆盖任意协议或全部服务类型，也不自动认定安全、可恢复、依法可用或获准变更。技术访问控制、软件使用许可、组织变更批准和用户授权是不同事项；这里只按取得的任务材料分别记录。

## 来源与已核范围

| 来源 | 版本、实际正文位置 | 可支持的范围 |
|---|---|---|
| [T1：IETF RFC 9110，HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) | June 2022，STD 97；15.3.1、15.3.3、15.5.2、15.5.4、15.5.5；正文查阅 2026-11-17 | HTTP状态码语义；实际应用是否遵守及业务终点须另核 |
| [T2：Google SRE Book，第4章 Service Level Objectives](https://sre.google/sre-book/service-level-objectives/) | 官方在线章，无本包可锁定的独立修订号；Indicators、Objectives、Agreements、Collecting Indicators、Aggregation；正文查阅 2026-11-17 | SLI、SLO、SLA及测量位置和聚合口径的专业用法；不采用章中产品指标为当前产品承诺 |
| [T3：Google SRE Book，第22章 Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) | 官方在线章，无独立修订号；重试／负荷相关段落、Test Noncritical Backends、Immediate Steps to Address Cascading Failures；正文查阅 2026-11-17 | 该章讨论的级联及恢复条件；不是对当前系统原因的诊断 |

T1 中，200的响应内容含义依请求方法；202表示已接受而处理未完成。401涉及有效认证凭据不足，403是服务器拒绝履行且不必只因凭据；404也可能是不愿透露资源存在。这些协议结果不等同于业务或制度结论。[T1](https://www.rfc-editor.org/rfc/rfc9110.html)

T2 将指标、目标与含后果的协议分开；服务端测量可能遗漏客户端问题，聚合窗口也会影响解释。T3 区分进程健康和服务健康，并说明恢复动作可能因负荷转移或启动条件而加剧故障。[T2](https://sre.google/sre-book/service-level-objectives/)、[T3](https://sre.google/sre-book/addressing-cascading-failures/)

## 名词、角色和动作关系

表内是核对任务的工作接口，不能当成新的协议要求。

| 说法 | 应保留的区别与动作关系 | 现实取证位置 |
|---|---|---|
| “服务可用” | 哪个调用方在什么负荷下完成哪个任务；单次成功与窗口内指标分开 | 客户端／服务端事件、业务结果、明确纳入规则 |
| “健康” | 进程响应、特定请求能服务、依赖正常、用户能完成任务 | 健康检查配置、探测位置、任务日志；不以一个绿灯代全部结果 |
| “已接受／已完成” | 接收请求、排队、执行、持久化或外部生效 | 请求ID、作业状态、结果核对及实际任务终点 |
| “备份／备用” | 有副本、可访问、能切换、可恢复到所需状态 | 依赖清单、凭据／权限、恢复演练、数据和容量核验 |
| “恢复” | 进程重启、部分功能恢复、目标负荷下恢复、余量重建 | 恢复判据及逐阶段观测；每个终点分列 |
| “许可／有权限” | 凭据有效、访问控制允许、组织授权、软件许可或其他适用规则 | 与具体动作对应的策略、批准或许可材料；HTTP成功不代证 |
| “降级” | 减少哪些工作或质量、谁受影响、哪些目标仍满足 | 实际降级策略、流量分类、用户结果和结束条件 |

调用方、网关、服务进程、依赖服务、调度器、值班人员和变更批准人可参与同一任务，但不是同一种角色。服务进程的“拒绝”是协议或程序行为，不据此赋予系统人格、意图或道德责任；人的操作和责任安排另有材料。

## 字段、单位、分母与时间

以下是本包建议的工作字段，按任务选取；不是 RFC 或 Google 文档的标准结构。

| 字段 | 用法与口径 |
|---|---|
| `service_version`、`endpoint`、`method`、`client_scope` | 记录版本、端点、方法和调用方范围；不同接口的成功不能互相替代 |
| `request_id`、`attempt_id`、`operation_id` | 原始请求、重试和后台操作分开；重试次数不自动变成独立用户任务数 |
| `received_at`、`accepted_at`、`completed_at`、`observed_at` | 接收、接受、完成和观测时间；时钟偏差、时区和无法确定的时间单列 |
| `status_code`、`business_result`、`result_evidence` | HTTP结果和任务结果分别保存；应用不遵守状态码语义时列实际观察与实现问题 |
| `sli_definition`、`window`、`numerator`、`denominator` | 明示成功判据、请求或时间口径、排除项、采样和缺失；分母改变要重新比较 |
| `latency_unit`、`aggregation`、`measurement_point` | 毫秒等单位、百分位或平均、客户端或服务端；平均值不替尾延迟 |
| `offered_load`、`attempt_rate`、`capacity_basis` | 用户任务负荷与包含重试的尝试率分开；容量来自何种负荷条件和测试 |
| `dependency`、`failure_scope`、`shared_failure_cause` | 有证据的依赖及共同故障条件；同一时刻报警不自动证明传播路径 |
| `recovery_endpoint`、`recovery_window`、`remaining_limit` | 恢复任务、时间窗和剩余限制；部分恢复可成立，不抹成全无或全部成功 |
| `allowed_operation`、`authority_basis`、`rollback_condition` | 实际动作范围、授权来源、停止／回滚条件；建议可行不表示已获准执行 |

观测缺失要保留缺口。例如没有客户端日志时，可报告服务端已观察到的结果，但不能据此计算未观测用户的完成率。总体请求成功率也不能自动替代某个受影响调用方的体验。

## 专业方法与处理步骤

先以 T1 和实际 API 版本解释协议结果，再核对用户所要的任务终点。收到202时读取相应操作状态或结果证据；没有完成证据就保留待核，不能重复提交以假装已完成。是否能重试须使用该具体操作的语义和既有重试策略，本包不从任意超时推出安全重试。

服务目标核对采用实际 SLI 定义，列清测量点、时间窗和分母。使用新口径前保留旧口径结果；达成服务端目标与客户端任务失败可以同时存在，并非必须择一。

维护分析先检查负荷、依赖和故障范围，再提出有条件的恢复候选。T3 中的措施只能在当前系统机制、影响范围及执行资格成立时采用；本包不提供“一律重启”“无限重试”或“直接切流”的默认动作。给方案时说明恢复起步需要哪些仍可用的服务、容量、资料和操作通路，再核对恢复后的任务结果。

## 与理论的有限对应

| 对应身份 | 可借用的区别 | 对应边界 |
|---|---|---|
| 部分对应，待检验 | §6.5 的维护问题连接备用、切换条件和恢复依赖 | 副本数不直接证明独立性；图中有环也不自动证明无法恢复 |
| 观察接口，待检验 | §6.13 的传播问题连接事件时间、调用依赖和负荷转移证据 | 多处同时报警可来自共同原因；不能只按时间先后认定级联 |
| 领域定位 | 附录 D.28；正式表述转义按 §3.4.1 另核 | HTTP请求成功、可用性目标和实际操作许可均保留领域含义 |

SLI是明示测量，不是系统全部状态；SLO不是已经达成的事实；服务组件不直接对应人的意愿或责任。这里没有把协议符合性等同于互通、压力下可靠或规范许可。

## 输出例与容易混淆的反例

**教学设定，非真实运维记录。** 某导出任务在10:00收到202，10:05后台记录仍为排队；同窗口健康端点返回200。随后更改访问规则的维护建议尚未取得该动作的批准材料。

可输出：“导出请求已接受，但截至10:05尚无完成依据；健康端点的200不能替代导出结果。可继续核对该操作ID和结果位置。访问规则是否可改由相应授权材料决定，当前观测只说明技术状态，不能把建议写成已经执行或已获准执行。”

反例：任务若只是确认请求已被系统接受，202已经可能满足该任务终点，不必追加全业务完成条件。某调用方因访问控制被403拒绝，也不能直接断言整个服务宕机，或断言该用户在制度上必定无权。又如两个备用实例共享同一必要依赖，实例数量不证明能承受该依赖失效；实际独立性仍需依赖材料。

## 变更复核与退出

RFC勘误或所用协议语义、API版本、SLI定义、路由、依赖、访问策略、授权、恢复判据或观测窗口变化时复核相关结论。在线 SRE 章节更新时核对被用到的段落，不把其历史产品举例当当前服务承诺。真实日志不能支持原因时先报告症状和竞争解释；超出 HTTP 服务任务时保留有效局部事实，另接相应标准和专业方法。
